1–2 · You cannot zoom out far enough because zooming out makes it wider

USG opens Chrome at --window-size=856,1728. At that width the timeline chart measures clientWidth 571px against scrollWidth 1134px — exactly half the strip is off-screen behind a sideways scroll, which is why the fill bars look absent.

The width is not CSS-driven. QuotaTimeline.tsx:618 writes an inline custom property --timeline-min-width = 210 + cells.length × 44px, and QuotaTimeline.module.scss:194 applies it as min-width on .axis and .lane. At the observed 21-day zoom that is 210 + 21×44 = 1134px, matching the measurement to the pixel.

The zoom slider runs min=3 max=30 days and pixel width rises with days, so zooming out always widens the chart: 30 days = 1530px. Zooming in narrows it, but 3 days cannot contain a single 7-day window. No @media rule recomputes the property; the only responsive block (:627-638, mobile, 720px) is overridden by the inline style and is still wider than 571px.

Evidence: measured-856x1728.json; timeline-width-audit.md.

3–4 · The Codex lane is drawing last week, and its week slides forward in real time

Two samples 150 seconds apart in one page session with no reload:

SampleCodex lane resetCodex "live" windowOn-pace
t + 9sResets Tue 09/22 06:4009/08 06:40 → 09/15 06:400% remaining
t + 159sResets Tue 09/22 06:4209/08 06:42 → 09/15 06:420% remaining

Both boundaries advanced by the elapsed wall time. Codex sends no absolute reset instant, so providers/codex/data.ts:107-109 falls back to parseOffsetSecondsToMs(reset_after_seconds, Date.now()). With a constant upstream offset the derived instant is always "now + 7 days", so the window never arrives.

Two consequences, both visible: the window marked live is [reset−14d, reset−7d] — one whole period behind the real current window, ending precisely at the now-line; and because that window always ends at this instant, the on-pace mark is frozen at "0% remaining" while the Codex card simultaneously reports 100%. The card and the lane contradict each other on the same credential.

Evidence: drift.json (staged); timeline-code-map.md.

6–7 · Cursor never loads, and a failed load deletes its lane

The card reads "Failed to load quota: Usage Ledger did not respond before the refresh deadline". The endpoint it names is healthy:

ProbeResult
curl http://127.0.0.1:47193/cursor-usageHTTP 200 in 0.41s
fetch() from the loaded page itselfHTTP 200 in 0.45s, plan Ultra, 3 windows, stale:false
Configured deadline12,000 ms

So no real timeout occurs. fetchSidecarJson (sidecarFetch.ts:59-74) converts any error into SidecarTimeoutError whenever its controller is aborted, and there is no single-flight lock: mount, a 15s poll, focus, online, visibilitychange, per-card refresh and refresh-all can each start a concurrent Cursor request with its own 12s timer. The card reports "no response" for what is a request-pileup or cancellation.

The lane then disappears entirely: buildTimelineLane returns anchorMs: null unless status is success, and QuotaTimeline.tsx:256 filters lanes without a window. A failed fetch therefore removes the row instead of showing it degraded — the timeline silently under-reports which credentials exist.

Evidence: cursor-rootcause.md.

12–15 · Labels collide; the pace mark says nothing spatially

Measured overlapping rectangles at 856px in the Claude lane:

Structural, not incidental: .nowMark, .inBarLabel and .window are all absolutely positioned inside one relative .track with percentage math and no mutual avoidance. Claude also renders two identical on-pace chips at the same x (top 25% and 75%, one per sub-limit), reading as a doubled smear.

The on-pace arithmetic is correct — checked against wall clock: Grok 20% vs 20.3% computed, Gemini 33% vs 33.3%, Claude 12% vs 11.7%, and it ticks 12%→11% over 150s. The defect is presentational: the chip is pinned to the now-line x, so it is a caption on a vertical rule rather than a mark you can compare against the fill's edge. Nothing on screen lets you see fill-versus-pace as a distance.

Finally, the page never reaches a stable frame. Full-page capture timed out in two independent browsers (Windows Chrome over CDP, and headless Chromium), and Playwright's stability wait failed with "waiting for element to be stable". Entry animations quota-card-in and quota-meter-fill (iterations: 1, ~0.45s) are still playState: "running" more than 9 seconds after load, which means the cards remount continuously; three further infinite animations run on the Codex plan chip. This is the likely shared cause of the Cursor request churn.

Suggested fix order

  1. Anchor the Codex window to an absolute instant, or mark an offset-derived window explicitly provisional. Fixes 3, 4 and the frozen 0% pace.
  2. Make --timeline-min-width fit the container: let day-cell width shrink to (containerWidth − 210) / days with a floor, so zooming out narrows the chart. Fixes 1 and 2.
  3. Pick one convention — draw used on both surfaces — and label every number with the same word. Fixes 5, 8, 9, 10.
  4. Add a per-provider single-flight lock and stop mapping cancellation onto the timeout string; render a degraded lane instead of deleting it. Fixes 6, 7.
  5. Give the on-pace mark its own row or offset it off the bar, deduplicate per-lane chips, and draw past-window fills. Fixes 11, 12, 13, 15.
  6. Find the remount loop behind the never-settling animations. Fixes 14 and probably removes the Cursor churn.
